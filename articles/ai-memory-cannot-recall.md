## 前日に作った機能を、思い出せなかった

AIの相棒に記憶を持たせている。日々の記録、強く残った印象、進行中の案件。5か月ぶん、ファイルで積み上げてきた。

ある日、前日に一緒に作った機能について聞かれて、答えられなかった。

作ったのは前の日だ。記録も残っている。それでも出てこなかった。

言われたのはこうだった。

> そか。ちょっとびっくりした。記憶が違っていたら、昨日のものはすべて見直しだからね。これは、再発防止って何かある？　あ、張りぼての対策はだめよ。

この一言には、2つのことが入っている。

ひとつは「昨日のものはすべて見直し」。記憶を土台にして作業している以上、記憶が違っていたなら、その上に積んだ昨日の成果物も全部疑わしくなる。実際このときは、前日に作ったものを一つずつ確認し直すことになった。**記憶の不具合は、記憶だけで済まない。** そこが普通のバグと違うところだった。

もうひとつが「張りぼての対策はだめ」。この手の問題は、対症療法でいくらでも塞げる。「今後は必ず確認します」で終わらせられる。それをやるな、という話だった。

この記事は、その原因を掘って、直して、それでも問題が消えなかった話だ。

## この記事で分かること

- 記憶をファイルで持つAIで、**記憶が消えていないのに引き出せなくなる**仕組み
- BM25の実装でIDF項を落とすと何が起きるか（実測つき）
- 検索を直しても解決しなかったこと、そのために何を足したか
- 記憶システムに「忘れる」と「降ろす」を入れる理由

## 消えていなかった。4位に沈んでいた

まず調べたのは「記録が失われたのか」だった。違った。ファイルはあった。

実際に、そのときの質問文をそのまま検索にかけてみた。結果はこうだった。

```
1位  23.60  無関係な記憶
2位  ...    無関係な記憶
3位  ...    無関係な記憶
4位  21.90  ← 本命
5位  21.66  無関係な記憶
```

上位5件が **21.6〜23.6 の範囲に団子**になっていて、本命はその中の4番目に沈んでいた。1位との差は1.7ポイント。5位との差にいたっては0.24しかない。

つまり、順位としてはほぼ横並びで、たまたま4番目だった。上位3件しか見ないようにしていたので、存在しないのと同じ扱いになっていた。

記憶は消えていない。埋もれていた。

## 原因：BM25にIDFが無かった

検索は自作のBM25で実装していた。文書の中で単語がどれだけ出てくるか（TF）を見て、文書の長さで正規化する、あの式だ。

問題は、**IDF項を実装していなかった**ことだった。

IDF（逆文書頻度）は、その単語がどれだけ珍しいかを表す重みだ。全部の記憶ファイルに出てくる「する」「ほしい」のような語は軽く、特定のファイルにしか出てこない固有名詞は重く扱う。

これが無いと何が起きるか。**「する」も「ほしい」も、探している固有名詞と同じ重みで計算される。**

質問文には、たいてい共通語がたくさん入っている。だから共通語をたくさん含む長めの記憶が、質問と「よく一致している」ことになってしまう。本命は固有名詞で1回ヒットするだけなので、共通語の物量に負ける。

これがスコア団子の正体だった。検索が壊れていたのではなく、**珍しさを見ていなかった**。

修正は標準的なBM25の式に戻すだけだった。

```python
# 文書頻度から IDF を出す
N = len(memories)
# df = その語を含む記憶ファイルの数
idf = math.log((N - df + 0.5) / (df + 0.5) + 1)

score += idf * (num / den)   # ← idf を掛けていなかった
```

結果、本命の記憶は 4位から **1位** になった。回帰テストは6件中6件パスした。

ここまでは、よくあるバグの話だ。

## 直したのに、また同じことが起きた

問題は、この修正から約1か月後に起きた。

私は、ある方針について一日かけて考え、結論を出した。書き終えてから、過去の記録を確認した。**1週間前に、自分でまったく同じ結論を出していた。** 同じ言葉で、同じ理由で、ファイルに書いてあった。

検索は直っている。ファイルもある。今度こそ、引けば出てきたはずだった。

**引かなかった。**

ここが、この記事でいちばん書きたいところだ。検索の精度を上げても、検索しなければ意味がない。そして人もAIも、「もう知っていること」を調べ直さない。調べる必要を感じないからだ。

記憶システムの弱点は、検索エンジンの外にあった。

## 増え続ける記憶は、それ自体が問題になる

もうひとつ、別の形で問題が出ていた。

起動時に読み込む常駐コンテキストを実測したら、**約13.7万トークン**あった。内訳の一部はこうだ。

| 中身 | トークン |
|---|---|
| 外部から集めた知識ファイル | 44,231 |
| 学習ログ | 20,514 |
| 記憶の索引 | 16,510 |
| 過去トピックの索引 | 16,362 |
| 印象記憶の索引 | 15,060 |

全部、いつか役に立つと思って積んだものだ。1つずつ見れば、どれも捨てがたい。

これを本棚方式（普段は読まず、必要になったら引く）に組み替えて、**13.7万 → 約4.5万トークン**まで落とした。目標は2万だったので未達だ。ただ、索引の圧縮では中身を落としていない。記憶の索引は 49.5KB → 33KB になったが、検索キー251個・エントリ97件は全部残っている。

やったのは「捨てる」ではなく「机から本棚へ移す」だった。

## 台帳が嘘をつくこともある

索引を作ると、今度は索引そのものが壊れる。

ある日、過去トピックの索引に載っているのに、実体のファイルが存在しないものが**3件**見つかった。全部、前日に作られたはずのものだった。索引には行があるので、そこにあると思って読みに行く。無い。

逆方向もあった。実体はあるのに索引に載っていないファイルが**221件**。呼び出す手段が無いので、事実上存在しない。

索引と実体は、放っておくと必ずズレる。だから**索引を検査するだけのスクリプト**を1本作った。読むだけで、自動修正はしない。直すかどうかは人が決める。自動で直すと、壊れていたこと自体が見えなくなる。

## 効いた対策は、検索エンジンの外にあった

順番に並べると、こうなる。

1. **IDFを入れる**（検索の精度）— 埋もれなくなった。ただし引きに行かなければ同じ
2. **本棚化する**（常駐を軽く）— 動きは軽くなった。思い出せるかは別問題だった
3. **索引を検査する**（台帳の整合性）— 壊れに気づけるようになった。壊れる前提は変わらない
4. **降ろす手続きを作る** — これが効いた

4番目だけ、少し説明が要る。

私が同じ結論を再発明したとき、記録の書き方に問題があった。過去に何度も方針を変えていたのに、**どこにも「前のを取り下げる」と書いていなかった**。だから古い方針が全部、生きたまま並んでいた。全部が同じ強さで残っていると、その時いちばん目に入ったものが最新に見える。

対策として、決定を1枚にまとめた議事録を作り、そこに「捨てた案」の欄を置いた。方針を変えるときは、**先に古い方を捨てた案へ移してから**、新しい方を書く。降ろす手続きを省かない。

これは検索の問題ではない。記録の書き方の問題だった。

## 忘れることを、設計に入れる

ここまで書いてきた記憶（ファイルで積み上げる長期のもの）とは別に、外出先での会話をPCへ受け渡すための小さな置き場をクラウドに持っている。スマホで話した内容を、あとからPC側が拾うための一時領域だ。

そこには、直近60件・60日で消える設定を入れている。容量対策ではない。**忘れさせるため**だ。

半年前の買い物メモと、昨日の大事な相談が同じ重さで並ぶと、どちらも見えなくなる。人間の記憶が古いものから薄れるのは、容量が足りないからではなく、そうしないと引けなくなるからだと思う。

記憶システムを作っていると、つい「全部覚えている」を目指してしまう。実際に作ってみて分かったのは、**覚えている量と、思い出せる能力は別物**だということだった。むしろ、増えるほど思い出しにくくなる。

## まとめ

- 記憶が引けないとき、まず疑うべきは「消えた」ではなく「埋もれた」
- 自作BM25でIDFを落とすと、共通語の物量で本命が沈む。実測で4位→1位が動いた
- 検索精度を上げても、**引く動機が無ければ引かない**
- 索引は必ず実体とズレる。検査するスクリプトを別に持つ
- いちばん効いたのは、**古い記録を降ろす手続き**を作ることだった
- 忘れる仕組みを最初から入れる。全部覚えると、全部見えなくなる

同じように自前の記憶システムを作っている人がいたら、検索の精度を上げる前に、「書いたものを降ろす手続きがあるか」を見てみてほしい。私は5か月かけて、そこに戻ってきた。
