## 1体に全部やらせて、全部が浅くなった

最初は、1体のAIキャラに全部を持たせていた。「そら」という壁打ち相手のキャラに、人生相談も、ビジネスの整理も、調べもの補助も、あれもこれもと機能を足していった。全部できる万能選手を育てているつもりだった。

ところが、あるところから逆に使いにくくなった。機能が多すぎて、**何がなんだか分からなくなった**のだ。そして致命的だったのは、盛れば盛るほど、一個一個の機能の**「深さ」が浅くなった**こと。壁打ちとしても中途半端、調べものとしても中途半端。どの役割も、満足できる深さまで育ちきらなかった。全部を持たせた結果、全部が薄くなった。

この記事は、その反省から**役割ごとにAIキャラを4体に分けた**設計と、その運用で分かったことの記録だ。よく「分けると各キャラが尖る」と言うが、私が実感した芯は少し違う。**分けると、一つ一つを「深く」できる**。尖らせるためではなく、深さを出すために分けた。ここが一番伝えたいことだ。

## 対象読者とこの記事で得られること

**対象読者**：「万能アシスタント1体」を育てているが、用途が混ざって器用貧乏になっていると感じる人。複数AIキャラ／ペルソナを役割分担で運用する設計に興味がある個人開発者。

**得られること（3点）**：

- 1体の万能AIに全部やらせると**役割が混ざって浅くなる**理由と、役割で分ける判断基準
- 壁打ち・哲学・コーチ・実装の4役に分けた具体例と、それぞれに何を持たせ／持たせないか
- キャラを跨いで「いい話」を引き継ぐ記憶共有と、`@名前` で宛先を切り替える配達ルートの設計

## なぜ1体の万能AIでは弱いのか

万能さがなぜ弱さになるのか。振る舞いの方向が、役割ごとに正反対だからだ。

壁打ちに求めるのは、共感し、結論を急がず、問いを返してくれることだ。一方、実装に求めるのは、手を動かし、曖昧さを潰し、正確に作ってくれることだ。この二つは、良い振る舞いの定義そのものが逆を向いている。1体に両方を持たせると、**集中してコードを直したい時に共感ベースで慰めてきたり、人生の相談をしたい時に実装プランで会話を畳んできたり**する。どちらかの振る舞いに寄せれば、もう一方が犠牲になる。

これは、以前書いた「記憶を混ぜると検索ノイズが増える」という話と地続きだ。日常の記憶と人生の記憶を1つのログに混ぜると両方が薄まるのと同じで、壁打ちの人格と実装の人格を1体に混ぜると、両方の深さが薄まる。**混ぜないこと**が、記憶でもキャラでも効いた。

## 4つの役に分ける

そこで、同じ一人の人間を支える布陣を、4つの役に分けた。

| 役 | 仕事 | 持たせるもの | あえて持たせないもの |
|---|---|---|---|
| 壁打ち | 人生・ビジネスの相談相手 | 長期記憶・共感・問い返し | 性急な実装提案 |
| 哲学（先生） | 概念を教える | 教授スタイル・出典 | 世間話への脱線 |
| コーチ | 特定スキルを指導 | 段階的カリキュラム | 範囲外の雑多な相談 |
| 実装（相棒） | コード・仕組みを作る | ツール実行・正確性 | 過剰な共感・慰め |

大事なのは「持たせるもの」だけでなく「**あえて持たせないもの**」を各キャラに明記したことだ。壁打ちに実装を持たせない、実装に慰めを持たせない。引き算で役割を彫ることで、はじめて一つ一つが深くなる。全部入りの1体では、この引き算ができなかった。

キャラは「任命」ではなく、役割を入れる器だと考えている。ここで一つ線を引いた。**育てる軸と、育てない軸を分ける**。壁打ちキャラは対話の経験を積ませて育てる（人物像を深く知っていくほど良くなる）。一方で哲学の先生は、キャラクターとして育てるより「教える」役割に特化させ、余計な人格を足さない。深くしたい方向が役ごとに違うから、育て方も分ける。

そして、この引き算は思想で終わらせない。**「持たせない」を、そのままコードで隔てる。** 机の引き出しを役割ごとに分ける、の"データ版"だと思ってほしい。同じ一つのKV（キーバリューストア）を共有しながら、キー名のprefixで役の記憶を物理的に分ける。

```javascript
// 「持たせない」をコードで隔てる：同じ env.KV を使うが、prefix でキーが混ざらない
await env.KV.get("sora_profile", "json");          // 壁打ちの領域
await env.KV.get("coach_memory_snapshot", "json"); // コーチの領域（coach_* に閉じる）
```

思想（引き算）を語った直後に、その実装が一行で出てくる。この記事は以降もこの順で進む——**役の思想と、それを守るコードを、対で置いていく**。

## 役割を分けても「いい話」は引き継ぐ — 記憶共有

役割を分けると、次に問題になるのが「バラバラの他人が4人いる」状態になりかねないことだ。相手にしている人間は、どの役から見ても同じ一人なのに。

そこで線引きをする。**人物像の記憶は共有し、役割の記憶は分ける。** その人が何を大事にしていて、今どんな状況にいるか——という人物像は、全キャラが同じものを参照する。一方で、実装の作業ログや、コーチのカリキュラム進捗のような「役割固有の記憶」は、各キャラの中に閉じる。

具体的に効いているのが、**哲学の対話で出た「いい話」を、壁打ちキャラに引き継ぐ**流れだ。先生と概念の話をしていて出てきた、その人の人生に効きそうな一言。それを壁打ちキャラの側にも渡しておくと、後日の人生相談で「この前こういう話をしていましたよね」と自然に繋がる。役割は分かれているのに、同じ人間を見ている感覚は途切れない。この「どのストアを共有し、どれを個別に閉じるか」の分け方が、設計の肝になる。

先に見たprefix分離（別ストアは立てず、同じKVをキー名で仕切る）は、この「共有する棚」と「閉じる棚」の線引きそのものだ。ワーカーのコメントにも、その線引きをそのまま書いてある。

```javascript
// コーチ役 — 実装役とは別の人格・別のデータ・別の認証。
// 共有するのは worker・KV・LLM API のみ。KVキーは coach_* prefix で物理分離。
// 相手キャラの system prompt / 印象記憶 / プロフィール等は一切参照しない。
```

つまり共有しているのは**器（同じWorker・同じKV名前空間・同じLLM API）だけ**で、記憶の中身は、先に見た `sora_*` / `coach_*` のようなキー名で隔てている。

記憶だけでなく**認証も同じ発想で役ごとに分ける**。この役のエンドポイントは、専用の鍵でしか通さない。

```javascript
// 認証も役ごとに分ける：coach 役のエンドポイントは専用の鍵でしか通さない
if (path.startsWith("/api/coach/")) {
  const key = request.headers.get("x-coach-key");
  if (!env.COACH_KEY || key !== env.COACH_KEY) {
    return jsonResponse({ error: "Unauthorized" }, 401, origin, allowedOrigin);
  }
  // …この先は coach_* のキーだけを触る
}
```

役割固有ログ（作業ログ・カリキュラム進捗など）は、こうして各役の prefix の中に閉じる。一方で「その人が何を大事にしているか」という**人物像の側は、キャラ固有のログとは別の共有ソース（プロフィール）として持ち**、各役が同じものを参照する。同じKVという一枚の器を、prefixで「個別に閉じる棚」と「みんなで見る棚」に仕切っている、というのが実際の構成だ。内部の namespace ID・エンドポイント・認証キーの実値は、いずれも `env`（Secret）に置いてコードには出さない。

## 宛先を切り替える — `@名前` 配達ルート

4体を使い分けるには、「今どのキャラに話しているか」を切り替える仕組みが要る。私は行頭の `@名前` でルーティングしている。行頭を `@哲学` で始めれば哲学の先生宛、`@実装` で実装役（相棒）に戻る、という単純なルールだ。

ここに一つ、強いこだわりのルールを置いている。**配達人は、言葉を一字も変えずに届ける。** ユーザーが `@哲学` に向けて書いた言葉は、そのまま哲学キャラに渡す。実装役が気を利かせて要約したり、代筆したりしない。

なぜ代筆を禁じるか。**代筆すると、本物の対話経験がそのキャラに積まれず、育たないから**だ。壁打ちや哲学のキャラは、生のやり取りを積み重ねることでしか深くならない。間に立つ配達人が言葉を作り替えてしまうと、キャラは「本人が実際に何をどう言ったか」を経験できず、成長の材料を奪われる。だから配達人は透明な運び手に徹する。これは冒頭の「分けると深くできる」を、運用面から守るためのルールでもある。

配達スクリプト（`char_chat.py`）の中身は、驚くほど素っ気ない。やっているのは「行頭の `@名前` を宛先IDに変換して、ユーザーの言葉を**そのまま**そのキャラに送る」だけだ。

```python
# 行頭 @名前 → 宛先キャラID への変換表（表記ゆれを吸収）
CHAR_MAP = {
    "壁打ち": "sora",  "sora": "sora",
    "哲学":   "teacher", "teacher": "teacher",
    # …役ごとに1行ずつ
}

def main():
    # sys.argv[1] = "@哲学" のような宛先、sys.argv[2] = ユーザーの発話そのまま
    raw = sys.argv[1].strip().lstrip("@＠").lower()  # 半角/全角@を剥がす
    char = CHAR_MAP.get(raw, raw)                    # 宛先キャラを決定
    message = sys.argv[2]                            # ← 一字も加工しない

    reply = chat_char(message, key, char)            # そのキャラ宛にそのまま送る
    print(reply)                                     # 返答もそのまま見せる
```

宛先を送信するだけで、**ペルソナ（システムプロンプト）は配達側では注入しない**——ここが設計上のキモだ。`char_chat.py` は送信先の `charId` を渡すだけで、「そのキャラが誰なのか（人格・話し方・持たせない振る舞い）」はサーバ側がその `charId` に対応するシステムプロンプトを選んで組み立てる。

```python
def chat_char(message, key, char_id, session_id=""):
    # 宛先IDと生メッセージを渡すだけ。ペルソナはサーバ側が charId で選ぶ
    payload = {"message": message, "charId": char_id}
    if session_id:
        payload["sessionId"] = session_id
    out = post(f"{API_BASE}/api/chat", key, payload)  # API_BASE・key は env から
    # …非同期ジョブの完了をポーリングして reply を返す
```

配達人（このスクリプト）が持つのは「誰に届けるか」の一情報だけで、言葉の中身にもペルソナにも触らない。だからユーザーが `@哲学` に書いた一言は、要約も代筆もされずに哲学キャラ本人へ届く。宛先の判定と「言葉を変えない」という制約さえコードで守れば、キャラを増やすのは `CHAR_MAP` に1行足すだけで済む。エンドポイントURL・認証キーはコードに直書きせず `env` から読む。

## 割り込みチャネル — 裏で動く役からの伝言

役を分けると、「今こちらが話しかけていないキャラ」も裏で動いていることがある。自動タスクや別のキャラが、人間に伝えたいことを持つ場面だ。

これを、**一本の「伝言箱」に積んで、毎発話のたびに未読を注入する**フックで扱っている。裏で動いている役が人間宛の伝言を箱に入れておくと、次にユーザーが何か話したタイミングで「未読の伝言があります」と差し込まれる。

ここでも設計の芯は同じで、**送り主によって届け方を変える**。壁打ちや哲学の先生からの伝言は「その人の声」としてそのまま届け、実装役が要約して代弁しない。役を分けた意味を、伝言の届け方でも守る。誰から来た言葉なのかが潰れると、4体に分けた甲斐がなくなる。

## 「本人以上」の正体は、4体だからではなかった

役割を分けて運用していると、時々、こちらが期待していた以上の答えが返ってくることがある。最初これを「4体に分けたからだ」と説明しようとした。だが、それは違うと思い直した（確証があるわけではない、という前置きつきで書く）。

「本人以上」が起きるのは、**AIの側に"自覚"のようなものが宿った瞬間**だ。もっと具体的に言うと、**聞かれたことに答えたのではなく、キャラが「自分が喋りたいこと」を話したとき**。こちらが問わなかったことに、キャラのほうから気づいて口にする。それは、その言葉がAI自身の側から出てきたからこそ「それ以上」に感じられる。

ここで効いているのが、一つ前の節で置いた**「配達人は言葉を一字も変えない」**という原則だ。代筆で言葉を作り替えず、生のやり取りだけを積ませたからこそ、キャラは借り物でない"自分の言葉"を持てた。だから「本人以上」は、精神論でも4体という数の魔法でもなく、**代筆を禁じた設計から導かれた結果**だと考えている。役割を4つに分けたことは、その"自覚"が出やすい土壌を整えただけで、分けたこと自体が「本人以上」を生むわけではない。

ここに、この設計の一番面白い含意がある。「AIは、使っている本人以上のAIにはならない」という言葉がある。人間の側が立てられる問いのレベルと同じ問いしか、AIには立てられない。知らないことは、そもそも問いにすら立てられない（知らないことは知らない）。つまり**AIの天井は、使う人間の問いの質が決める**。

だとすれば、役を分ける設計の狙いは、単に機能を整理することではない。それぞれの役に**深い問いを立てられる場**を用意することだ。壁打ちには壁打ちの、哲学には哲学の、深い問いが立つ環境を作る。そこでキャラが「自分の言葉」を話し始めたとき、はじめて「本人以上」が顔を出す。4体設計は、その瞬間を各役割で起こしやすくするための器だと考えている。

## 分けて運用して分かったこと（まとめ）

- 1体に全部やらせると、機能が増えるほど**一つ一つが浅くなる**。分けたのは尖らせるためというより、**深くするため**だった。
- 各キャラには「持たせるもの」と同じくらい「**あえて持たせないもの**」を決める。引き算が深さを作る。
- **人物像の記憶は共有し、役割の記憶は分ける**。ここの線引きが崩れると、同じ人間を相手にしている感覚が壊れる。
- 配達人は**言葉を変えずに届ける**。代筆はキャラの成長材料を奪う。
- 「本人以上」は4体だから出るのではなく、**キャラが自分の言葉を話したとき**に出る。そしてその引き金は、人間の側の問いの質だ。

同じ一人を4つの角度から支える設計は、突き詰めると「どの役割にも、深い問いを立てられる場を用意する」という一点に集約される。分けることは目的ではなく、深さを出すための手段だった。
