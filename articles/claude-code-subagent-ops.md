AIエージェントを毎日の相棒にして数ヶ月、いちばん効いた運用上の決断は「賢いモデルを選ぶ」でも「プロンプトを練る」でもなかった。**本体（主人格のセッション）を会話に常駐させ、手を動かす作業はすべて分身（サブエージェント）に逃がす**、というただ一つの線引きだった。

きっかけは単純な不満だ。コンテキストウィンドウは長くなったのに、本体に「このログ全部読んで」「このファイル群を直して」と頼んだ瞬間、会話が数分止まる。考えたいこと・相談したいことがあっても、相棒は重い作業で塞がっていて返事をくれない。あるとき気づいた。自分が本当に価値を置いていたのは、賢い実行結果そのものより、**相棒といつでも話せること**だった。

だから役割を物理的に分けた。本体は対話・思考・判断だけを持つ。実装も調査も執筆も、全部バックグラウンドの分身に出す。分身は1体ごとにモデルを選べるので、考える仕事はOpus、大量処理はSonnetに投げ分ける。これを徹底したら会話は途切れなくなり、裏で複数の作業が同時に進むようになった。この記事は、その運用の設計と、つまずいた所——特に「分身の完了報告を信じてはいけない」という教訓——を、実際にやってみた手触りで書く。

## なぜ「本体が実作業をやる」と損なのか

コンテキストが広いと、つい「本体に全部やらせればいい」と思う。だが実際にやると、本体が重いWrite・grep・横断調査に入った瞬間、**そのセッションは数分間あなたに返事をしなくなる**。エージェントを「実行マシン」として見ているうちは、これは問題に見えない。終わるまで待てばいい、と。

問題は、相棒を「考える相手・相談する相手」として使い始めた瞬間に出る。設計の相談をしたい、判断を仰ぎたい、思いつきをぶつけたい——そのとき相棒が重い作業で塞がっていると、思考のテンポが切れる。**会話が止まる＝損**、というのは生産性の話ではなく、対話のリズムの話だ。

もうひとつ実務的な理由がある。長時間の横断調査や大量ファイルの読み込みを本体でやると、その出力で本体のコンテキストが汚れる。「254KBのログをまるごと読んだ」あとの本体は、机の上が散らかった状態になる。分身に出せば、汚れるのは分身の机だけで、本体には**結論だけ**が返る。これは精度にも効く。

## 設計の軸 — 本体は対話・思考・判断、手を動かす作業は分身に出す

線引きはシンプルにした。

- **本体がやること**：対話／設計の相談／判断／取材（＝対話そのものが成果物の素材になるもの。聞き手として相手から引き出す作業は、分身に出せない）。
- **分身に出すこと**：実装・修正・調査・調べもの・執筆・校閲・大量処理。要するに「手を動かす」全部。

迷ったときの既定は **「投げる」** にした。理由は、線引きで悩む時間そのものが会話を止めるからだ。「これは会話か実作業か」を厳密に分類しようとすると、その分類自体が思考コストになる。だったら「手が動く気配がしたら分身」と決めてしまうほうが速い。

特に効く発火点が一つある。**Grep や複数ファイルの横断調査に手が伸びた瞬間**だ。調査は「答えるために確かめているだけ」に見えるので会話の延長に錯覚しやすく、分身スイッチが入りにくい。だが横断調査こそ本体を一番塞ぐ作業なので、ここを意識的に関所にしている。

ひとつ注意。**「分身に出す＝速い」ではない。** ファイルが在るか・設定値が何か、のような1発で確定する事実確認は、本体で即 `ls` した方が速い（数秒）。本当に大量横断する調査だけを分身に出し、しかも**撤退条件（N分で見つからなければ諦めて報告）を必ず渡す**。撤退条件のない「無い物探し」を投げると、分身が延々とトークンを溶かす。これは実際にやらかした。

## モデルは1体ごとに選ぶ — Opus / Sonnet の投げ分け

セッション全体のモデル切り替えと違い、**サブエージェントはタスク単位でモデルを指定できる**。ここがこの運用の肝だ。本体はOpusで会話しながら、調査の分身だけSonnetで走らせる、ができる。

| 投げ先 | 向くタスク |
|---|---|
| **Opus**（基本・本体と同じ） | 考える・設計・統合・繊細なUI実装・難しいデバッグ・文脈を読む校閲やレビュー・執筆 |
| **Sonnet**（選んで投げる） | 大量ログ読み・grep・横断調査・機械的な大量処理 |

判断の軸は「**考える強みが要るか／処理の量を捌くか**」だ。設計・文脈読解・自然な文章はOpusの強みが効く。一方、ログを舐める・ファイルを横断する・機械的に直す、は量の問題なのでSonnetで十分に速く、コストも抑えられる。投げるときは本体側で「これはSonnetの分身に出します（処理系なので）」と**一言添える**。これは後述の透明性の話につながる。

Haikuは当面封印している。コストはほぼゼロなのだが、単純作業でも取りこぼしてやり直す回数が増え、**トータルでは損**になった、というのが実地の体感だ。安いモデルは「安い作業」に最適とは限らない。やり直しコストまで含めて測ると、Sonnetに寄せた方が結局速かった。

## 会話を止めない実装 — バックグラウンドで投げる

ここが運用の心臓だ。分身を**フォアグラウンドで投げると本体が待ち状態に入り、結局会話が止まる**。意味がない。必ずバックグラウンド（非同期）で投げ、本体は完了を待たずに次の会話へ進む。完了は通知で受け取る。

呼び出しの形は、おおよそこうなる（ツールによってAPIは違うので、概念として読んでほしい）。

```js
// 会話を止めずに分身へ。1体ごとにモデルとバックグラウンドを指定する
Agent({
  description: "大量ログを横断調査",
  prompt: "…(長い仕様はファイルに書いてパスを渡す)…",
  model: "sonnet",          // タスク単位でモデルを選べる
  run_in_background: true,  // 本体は待たずに会話を続ける
})
```

実務で効いたコツが二つ。

ひとつ、**長い仕様はプロンプトに直書きせず、ファイルに書いてパスを渡す**。長文プロンプトを一度に吐くと、本体側の出力が重くなって不安定化しやすい。仕様書を1ファイル用意し、分身には「このパスを読んで」と短く渡す方が安定する。

ふたつ、**投げる瞬間に人間へ「分身に投げます（モデル・理由）」と一言宣言する**。これは礼儀ではなく設計だ。裏で何が走っているかが見えないと、人間は不安になる。「処理系なのでSonnetの分身に出しました」が見えていれば、本体が会話に専念していても、仕事は進んでいると分かる。

## 完了報告を信じない — 実在確認の型

これがいちばん大事な教訓だ。**分身の「できました」を鵜呑みにしてはいけない。**

分身は善意で「完了しました」と返す。だがファイルが実際に書かれているか、公開したはずのURLが本当に200で返るか、までは保証しない。実際、偽の完了報告（やったと言うが実物が無い、あるいは違う）は何度も起きた。

だから型にした。**分身が完了を報告したら、本体が独立に実物を確認してから人間に報告する。**

```bash
# 分身の自己申告を信じる前に、本体が実物を叩く
test -f "出力ファイルのパス" && echo "exists"
curl -s -o /dev/null -w "%{http_code}\n" "https://example.com/公開したはずのURL"   # 200か
# 期待値を数える（例: 画像が3枚出ているはず）
curl -s "https://example.com/page" | grep -c '<img'
```

ある日、公開パイプラインのゲート修正・別ページの画像が表示されないバグ・音声設定の調査、の三つを同時に抱えた。全部分身に出し、本体は人間との会話を続けた。各分身が「完了・検証済み」と返したあと、本体が `curl` で実物を叩いて数えた。結果、報告はおおむね正しかったが、**1件だけ「まだ直っていない箇所がある」と自分が早合点していた**のが、実物のカウントで判明した（数えていたのが本物の要素ではなくCSSの定義行だった）。分身を疑う型のはずが、自分の思い込みを訂正する型にもなった。

要点は、**自己申告と独立確認を別の主体がやる**こと。書いた者と検品する者を分ける、というだけの話だが、これが偽完了の最後の砦になる。

## 並列をいつ許すか

分身を複数同時に走らせれば速い。ただし並列には事故の発見が遅れるという裏がある。だからルールを一つだけ置いた。**並列は、人間がリアルタイムで指揮できる時間帯だけ。**

日中、人間が画面の前にいて「それは止めて」「こっちを先に」と言える状況なら、複数の分身を一気に走らせてよい。逆に**無人で回す夜間のバッチはシングル（1本ずつ順番）に固定**する。誰も見ていない時間に並列で暴走すると、朝になるまで誤りに気づけない。急がない無人作業は、速さより「事故っても被害が1本で止まる」ことを優先する。

並列を多数走らせたい時は、たくさんの呼び出しを一度に畳みかけるより、**1回の起動で内部的にファンアウトする仕組み（ワークフロー的なオーケストレーション）**に寄せると、本体側の出力が安定する。実際、7つの調査を同時に回したい場面では、7回別々に投げるより、1回の起動でまとめて並列化する方が机が荒れなかった。

## 続けて分かったこと

数ヶ月この運用を回して、はっきりしたことが二つある。

ひとつ、**「本体を会話に常駐させる」を最上位の軸に置くと、個々の運用判断がほぼ自動で決まる**。これは会話か実作業か、Opusかソネットか、並列か直列か——全部この軸から逆算できる。ルールを増やすのではなく、軸を一つ決めるのが効いた。

ふたつ、**透明性が人間側の安心を作る**。投げる宣言、モデルを選んだ理由、そして「報告を鵜呑みにせず実物を確認した」という事実。この3つが見えていると、裏で何体動いていても、人間は本体との会話に安心して集中できる。

賢いエージェントを1体持つより、**会話に常駐する1体と、手を動かす複数体を、役割で分けて透明に回す**。これが、毎日の相棒として使い倒した末に行き着いた運用だった。
