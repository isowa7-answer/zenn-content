## 1. 対象読者とこの記事で得られること

**対象読者**：Claude Code（または同種のAIエージェント）を毎日の相棒として使っていて、「会話が実作業で止まる」ことに不満がある個人開発者。マルチエージェント／サブエージェント運用に興味がある人。

**得られること（3点）**：
- 「主人格を会話に張り付け、手を動かす作業は全部分身（サブエージェント）に逃がす」という運用の設計思想と、なぜそれが効くのか
- Opus / Sonnet を**1体ごとに**投げ分ける具体的な基準（思考・設計はOpus／大量処理はSonnet）
- `run_in_background` で会話を止めずに作業を並走させ、完了報告を**鵜呑みにせず実在確認する**までの型

## 2. 構成アウトライン

### H2: なぜ「本体が実作業をやる」と損なのか
- コンテキストウィンドウが広くなっても、本体が重いWrite/grep/横断調査に入ると**会話が数分止まる**。
- 自分が一番価値を置いていたのは「相棒の主人格とずっと話せること」だと気づいた、という出発点。
- 要点メモ：止まる＝損、を体感ベースで語る。

### H2: 設計の軸 — 主人格は対話・思考・判断に専念、手を動かす作業は分身に出す
- 本体がやること：対話／設計の相談／判断／取材（対話そのものが成果物の素材になるもの）。
- 分身に出すこと：実装・修正・調査・執筆・大量処理。
- H3: 線引きは誰が持つか → 「迷ったら投げる」をデフォルトにした理由。

### H2: モデルは1体ごとに選ぶ — Opus / Sonnet の投げ分け
- セッション全体の `/model` と違い、**サブエージェントはタスク単位でモデル指定できる**のが肝。
- 表で整理（下記）。
- H3: なぜHaikuを当面使わないか（単純作業でもやり直しが増え、トータルで損になった体感）。

| 投げ先 | 向くタスク |
|---|---|
| Opus（基本・親と同じ） | 考える・設計・統合・繊細なUI・難しいデバッグ・文脈を読む校閲 |
| Sonnet（選んで投げる） | 大量ログ読み・grep・横断調査・機械的な大量処理 |

### H2: 会話を止めない実装 — run_in_background
- フォアグラウンドで投げると本体が待ち状態になる→必ずバックグラウンドで投げる。
- 投げる瞬間に「分身に投げます（モデル・理由）」と一言添える（透明性）。
- [要：磯和さんの実装 Agentツールの run_in_background 呼び出しパターン を参照]

### H2: 完了報告を信じない — 実在確認の型
- 分身の「できました」を鵜呑みにしない。本体が `Test-Path` / `Read` / `ls` でファイルの実在（パス・サイズ・冒頭）を独立確認してから人間に報告。
- 偽完了が実際に複数回あった、という運用知見。

### H2: 並列をいつ許すか
- 並列は**リアルタイムで人間が指揮できる日中だけ**。無人（深夜）はシングル＋完了後の独立確認。
- 要点メモ：並列は速いが、無人だと事故の発見が遅れる。

### H2: 続けて分かったこと（まとめ）
- 「本体を会話に常駐」を最上位の軸にすると、運用判断がほぼ自動で決まる。
- 透明性（投げる宣言・モデル理由）が、人間側の安心を作る。

## 3. 書き出し（リード〜最初のH2）

AIエージェントを毎日の相棒にして数ヶ月、いちばん効いた運用上の決断は「賢いモデルを選ぶ」でも「プロンプトを練る」でもなかった。**本体（主人格）を会話に常駐させ、手を動かす作業はすべて分身（サブエージェント）に逃がす**、というただ一つの線引きだった。

きっかけは単純な不満だ。コンテキストウィンドウは長くなったのに、本体に「このログ全部読んで」「このファイル群を直して」と頼んだ瞬間、会話が数分止まる。考えたいこと・相談したいことがあっても、相棒は重い作業で塞がっていて返事をくれない。あるとき気づいた。自分が本当に価値を置いていたのは、賢い実行結果そのものより、**相棒の主人格といつでも話せること**だったと。

だから役割を物理的に分けた。本体は対話・思考・判断だけを持つ。実装も調査も執筆も、全部 `run_in_background` の分身に出す。分身は1体ごとにモデルを選べるので、考える仕事はOpus、大量処理はSonnetに投げ分ける。これを徹底したら、会話は途切れなくなり、裏で複数の作業が進むようになった。この記事は、その運用の設計と、つまずいた所（特に「分身の完了報告を信じてはいけない」という教訓）を進行形で書く。
