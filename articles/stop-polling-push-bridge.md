## 7本のループが、ずっと聞きに行っていた

自宅のPCとクラウド側の間に、常駐プロセスを1本置いている。クラウドに溜まった仕事（メールの仕分け、チャットの返信など）をPC側に取ってくる橋渡し役だ。

作った当初から、仕組みはずっと同じだった。**一定間隔で聞きに行く。** いわゆるポーリングだ。

気づいたら、そのループが7本になっていた。

| ループ | 間隔 | 何を聞きに行っていたか |
|---|---|---|
| 心拍 | 60秒 | 自分の生存をクラウドに通知 |
| 定型作業の取得 | 2秒 | 予約された定型処理（記事生成・集計など）が入っていないか |
| メール処理 | 2秒 | 新着メールの仕分け依頼が来ていないか |
| チャット取得 | 0.3秒 | スマホから話しかけられていないか |
| チャット取得（並列2本目） | 0.3秒 | 同上（同時2件まで捌くため） |
| チャット取得（別系統） | 0.3秒 | 別キャラのチャット |
| 定型作業の取得（別系統） | 2秒 | 別キャラの定型処理 |

0.3秒のループが3本ある。1日は86,400秒なので、1本あたり28.8万回。全部足すと、**1日あたりおよそ66万回**。

数十万回叩いて、そのほとんどが「まだ何もありません」という返事を受け取るためだけに動いていた。CPUを食うほどではないが、何も起きていない時間にこれだけ動き続けている、という事実が気持ち悪かった。

（この66万回は「仕事が無いときも待機ループが回り続ける」という前提で間隔から計算した理論値だ。実際にはレスポンス待ちで多少減る。ただし桁は変わらない）

## この記事で分かること

- ポーリングを止めるとき、**止めていいかをどう測るか**
- 消さずに止める（環境変数で戻せる状態を残す）実装
- 「押してもらう」側に切り替えるときの、最小の受け口の作り方
- Cloudflare Workers でレスポンス後の非同期処理が消える落とし穴（実バグ）

## 止める前に、14日ぶんの実績を数えた

動いているものを止めるのは、新しく作るより怖い。止めた瞬間に何かが静かに壊れて、しばらく気づかない、というのがいちばん怖い。

なので、先に測った。**過去14日間で、各ループが実際に何件処理したか**を数えた。

結果はこうだった。

| ループ | 14日間の処理数 | 判定 |
|---|---|---|
| 定型作業の取得 | 0件（19日間ゼロ） | 止める |
| 定型作業の取得（別系統） | 0件（24日間ゼロ） | 止める |
| チャット取得×2（旧経路） | 26件（最終は数日前） | 止める |
| メール処理 | 565件 | 残す |
| チャット取得（現行） | 96件 | 残す |
| 心拍 | — （生存通知なので件数の概念なし） | 残す |

7本のうち **4本は、19日〜24日にわたって1件も処理していなかった**。0.3秒ごとに聞きに行っていたループが、である。

ついでに、ループとは別に動いていた「もう1台のPCの状態を見に行くGET」も止めた。見に行く先のPCを、2週間以上前から起動していなかった。これも測るまで気づかなかった。

「何かに使っているかもしれない」と思って残していたものが、実際には何もしていなかった。これは測らないと分からなかった。逆に、残すべき2本もはっきりした。

止めるかどうかを勘で決めなくて済んだのが、この計測のいちばんの価値だった。

## 消さずに止める

4本を止めるとき、コードは削除しなかった。**環境変数で復活できる形**にした。

```python
# 既定は全部OFF。環境変数を立てたときだけ起動する
if os.environ.get("SORA_BRIDGE_FUMI_TASK") == "1":
    tasks.append(fumi_task_poll_loop())

if os.environ.get("SORA_BRIDGE_MAIL_AI") == "1":
    tasks.append(mail_ai_poll_loop())

# ...以下同様に、ループごとに1つずつスイッチを持たせる
```

起動ログにも、いまどの状態かを出す。

```
ポーリング全停止=押しの配管へ移行
```

なぜ消さないか。**止めた判断が間違っていたときに、1秒で戻せるようにするため**だ。

コードを消すと、戻すのに再実装が要る。再実装が要ると、「まあ様子を見よう」と我慢してしまう。環境変数を1つ立てるだけで戻るなら、迷わず戻せる。**引き返せる状態を保ったまま前に進む**ほうが、結果的に大胆な変更ができる。

## 「押してもらう」側に変える

残した2本も、最終的には止めた。代わりに、クラウド側から**押してもらう**形にした。

受け口はこれだけだ。

```
POST /mail-ai     … メールの仕事が入ったよ、という合図
POST /fumi-chat   … チャットが来たよ、という合図
GET  /health      … 疎通確認
```

ポートは 8854。バインドは `127.0.0.1` のみで、LANからは直接叩けない。認証は `x-bridge-push-key` ヘッダと、`.env` に置いた鍵の一致だけ。

ここで大事な設計判断がひとつある。

**押しは「合図」に過ぎない。仕事の中身は運ばない。**

押されたPC側は、合図を受け取ってから、これまでと同じ経路（pending から claim する処理）で仕事を取りに行く。処理関数も、ポーリング時代のものをそのまま呼んでいる。二重に実装していない。

```python
# ポーリング側と同じ関数を import して使う
from sora_bridge import process_one_mail_ai_job, process_one_fumi_chat_job
```

こうしておくと、**押しが失敗しても、仕事は失われない**。合図が届かなかっただけで、仕事はクラウド側の pending に残ったままだ。環境変数でポーリングを1本復活させれば、溜まっていたぶんがそのまま流れる。

「押しが届かないと止まる」ではなく「押しが届かないと遅れる」。この差は大きい。

## 空になるまで回す

最初の実装では、押し1回につき仕事を1件だけ処理していた。2件同時に来ると、2件目が次の押しまで待つことになる。

なので、空になるまで回すようにした。

```python
MAX_DRAIN = 20

def drain(fn):
    count = 0
    while fn():          # 処理するものがある限り回す
        count += 1
        if count >= MAX_DRAIN:
            break        # 打ち切り。残りは次の押しで回収する
```

上限を入れているのは、万が一おかしくなったときに無限に回り続けないようにするためだ。処理関数がバグで常に「まだある」を返したら、上限が無ければそのまま暴走する。

20という数字は、実績から決めた。14日間でいちばん多かったメール処理が565件、1日あたり約40件。つまり半日ぶんが一度に溜まっても1回の押しで捌ける量になる。それ以上溜まっているなら、それは通常の遅延ではなく異常なので、一度打ち切って次の押しに回したほうが安全だと考えた。打ち切っても、残りは次の押しで拾える。

## Cloudflare Workers の落とし穴

押す側は Cloudflare Workers で書いた。ここで実際に踏んだバグがある。

最初、押す処理をこう書いていた。

```js
// ダメな書き方
pushBridge(payload);        // await していない
return new Response("ok");  // すぐレスポンスを返す
```

意図としては「押すのは片道でいいから、待たずにレスポンスを返す」だった。日本語で言えば fire-and-forget だ。

**押しが届かないことがあった。**

原因は、Cloudflare Workers がレスポンスを返した時点で、そのリクエストに紐づく非同期処理を打ち切るからだ。`await` していない `fetch` は、レスポンス後に実行される保証がない。運が良ければ届き、悪ければ消える。しかもエラーにならないので、気づきにくい。

正しくはこう書く。

```js
// レスポンス後も処理を続けてほしいと明示する
ctx.waitUntil(pushBridge(payload));
return new Response("ok");
```

`ctx.waitUntil()` に渡しておけば、レスポンスを返した後もその Promise の完了まで実行してくれる。

サーバーレス環境では、**レスポンスを返した後の世界がある保証はない**。バックグラウンドで走らせたい処理は、明示的にそう伝える必要がある。

## 結果

ポーリングを全部止めた2分後に、実際のメールが1通届いた。その仕事は押しで処理された。聞きに行く動作をゼロにしたまま、会話も処理も成立した。

得られたものを整理すると、こうなる。

- 理論値で1日66万回の空振りHTTPリクエストが消えた
- 常駐プロセスのCPU使用がほぼ待機だけになった
- 反応がむしろ速くなった（最大0.3秒の待ち時間が無くなったため）

## まとめ

- **止める前に測る。** 14日ぶんの実績を数えたら、7本中4本は19日以上ゼロ件だった
- **消さずに止める。** 環境変数で1秒で戻せる状態を残すと、大胆に止められる
- **押しは合図だけにする。** 中身を運ばなければ、押しが失敗しても仕事は失われず、遅れるだけで済む
- **処理関数は共用する。** 押し用に書き直すと、二重実装が必ず腐る
- **Cloudflare Workers では `ctx.waitUntil()`。** レスポンス後の非同期処理は、明示しないと消える

ポーリングは、書くのが簡単で、止めるのが難しい。止めるための材料（実績ログと、戻せるスイッチ）を先に用意しておくと、ずっと楽になる。
