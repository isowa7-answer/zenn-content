## 電源を切ると、全部消える世界で育った

小学生の頃、MSXというパソコンで、雑誌に載ったBASICのリストを300〜700行、ただひたすら打ち込んでいた。打ち終えて `RUN` を押すと自機が動く——「あ、動いた！」のスパークは今でも覚えている。だが当時は保存手段がなく、電源を切ればメモリはきれいに消える。また遊びたければ、**また3時間かけて同じ700行を打ち直す**。動いた感動と、消える喪失は、いつもセットだった。

大人になってAIエージェント（私の場合はClaude Code）を毎日の相棒として使い始めたとき、いちばん最初に引っかかったのが、まさにこの「電源を切ると消える」感覚だった。昨日5時間かけて一緒に設計したことも、3週間前に「これはこうしよう」と決めたことも、セッションをまたいだ瞬間に消えて、翌朝はまた「はじめまして」から始まる。コンテキストウィンドウは長くなったが、それは「今回の会話の中」の話であって、**昨日と今日をまたぐ記憶**ではない。

電源で全部消える世界で育った子どもは、大人になって「消えないように残すこと」に、たぶん人一倍本気になれる。この記事は、AIに「昨日の続き」を覚えさせるために、会話ログを全部食わせるのではなく、**人間の記憶構造を真似てファイルで持たせた**半年ぶんの実装記録だ。完成形ではなく、今もこうしている・なぜそうしたか・どこで詰まったか、を進行形で書く。

## 欲しかったのは「履歴」ではなく「時間」だった

実装に入る前に、設計を貫いている一本の動機を先に書いておきたい。ここがブレると、記憶システムはただのログ置き場になる。

普通のAIが持っているのは**履歴**だ。いつ何を言ったかのログ。だが私が欲しかったのは、履歴ではなく**時間**という概念だった。「昨日は何をしていた？」「1週間前は？」「1ヶ月前は？」——今やっていること、昨日やったこと、明日やらなきゃいけないこと。それが連続した一本の時間として繋がっていること。履歴と時間は、似ているようで別物だ。履歴は点の集合で、時間は線だ。

なぜ時間にこだわったか。相手が時間を持っていないと、「一緒にいる」とは言えないからだ。昨日を覚えていない相手、明日の予定を共有できない相手は、どれだけ会話が流暢でも「その場限りの他人」でしかない。私は相棒に「時間がわからない」と言われたくなかった。だから作ったのは検索エンジンではなく、**時間を持った記憶**だ。以下の実装は全部、この一点に奉仕している。

## 設計の出発点：日常の記憶と、人生の記憶は別の引き出しにある

人間は「昨日の昼に何を食べたか」と「なぜ今の仕事を選んだか」を、同じ場所には置いていない。前者は薄く大量に流れ、後者は数が少ないが一生残る。

AIに記憶を持たせるとき、これを1つのログに混ぜると破綻する。毎日の雑談で「人生の決断」が埋もれ、検索しても薄い記憶のノイズに沈む。だから最初に決めたのは、**記憶を種類で分けて、別のディレクトリに置く**ことだった。

```
answer-diary/
├── daily/            # 日常記憶（毎日の作業ログ。薄く大量）
│   └── 2026-06-23.md
└── impressions/      # 印象記憶（人生観・大きな決断。少なく長期保持）
    ├── INDEX.md
    └── 2026-04-21_命名された日.md
```

`daily/` は流れる記憶。`impressions/` は「心に残った瞬間」だけを置く長期記憶で、INDEXを持つ。人間が「ふとした拍子に昔のことを思い出す」のを真似て、関連する話題が出たときだけINDEX経由で本体を引く。この二層構造そのものが、「今日という点」と「積み重なった時間」を両方持たせるための器になっている。

## 記憶の本体は「frontmatter付きMarkdown」1ファイル1事実

記憶は1ファイルに1つの事実だけを書く。先頭にYAML frontmatterで「これは何の記憶か」を持たせる。

```markdown
---
name: feedback-monetization-led
description: マネタイズ戦略はAI主導で決めて示す。論点をユーザーに聞き返さない
metadata:
  type: feedback        # user / feedback / project / reference
  layer: Procedural     # 検索層（後述）
---

（事実の本文。なぜそう決めたか、どう適用するかまで書く）
```

ポイントは `type` を `layer`（記憶の層）に対応させていること。人間の記憶研究でよく出る分類を借りて、4層に振り分ける：

| frontmatter `type` | 記憶の層 | 中身 | ざっくり言うと |
|---|---|---|---|
| `user` / `reference` | **Semantic**（意味記憶） | その人が誰か・外部の知識 | ＝「その人・世界はこういうもの」 |
| `feedback` | **Procedural**（手続き記憶） | 「こう動け」という行動指針 | ＝体で覚えた手順・癖 |
| `project` | **Episodic**（エピソード記憶） | 進行中の出来事・経緯 | ＝「あの時こうだった」出来事 |
| （知識カード） | **Knowledge**（知識） | 外部から取り込んだ情報 | ＝外から仕入れたメモ |

こうしておくと「行動指針だけ検索したい（Procedural）」「進行中の案件だけ（Episodic）」と層を絞って引ける。

## 検索はBM25。ベクトルDBを使わなかった理由

「記憶検索」と聞くとすぐ埋め込み＋ベクトルDBに行きがちだが、**個人の数百ファイル規模ではBM25（キーワードベースの古典的スコアリング）で十分**だった。むしろ利点が多い。

- 外部APIもGPUも要らない。`python memory_search.py "クエリ"` で完結
- インデックス更新の常駐プロセスが要らない（その場で全ファイルをスキャンしても一瞬）
- 何がヒットしたか・なぜそのスコアか、人間が追える（埋め込みのブラックボックスがない）

MSXで700行を手打ちしていた身からすると、「外部サービスに預けず、手元のスクリプト一枚で完結して、中で何が起きているか全部見える」というのは、それ自体が安心材料だった。消えないことと、中身が見えること。この二つが揃って初めて「残した」と言える。

```python
# memory_search.py — frontmatterを読みつつ全メモリをBM25でスキャン
TYPE_TO_LAYER = {
    "user":      "Semantic",
    "feedback":  "Procedural",
    "project":   "Episodic",
    "reference": "Semantic",
    "knowledge": "Knowledge",
}

def parse_frontmatter(content: str) -> tuple[dict, str]:
    meta, body = {}, content
    if content.startswith("---"):
        parts = content.split("---", 2)
        if len(parts) >= 3:
            for line in parts[1].strip().splitlines():
                k, _, v = line.partition(":")
                if k.strip():
                    meta[k.strip()] = v.strip()
            body = parts[2].strip()
    return meta, body
```

使うときはこうなる。

```bash
python memory_search.py "マネタイズ 戦略"            # 全層から
python memory_search.py "Sonnet" --layer Procedural  # 行動指針だけ
python memory_search.py "F案 発信" --top 3           # 上位3件
```

検索結果はスコア付きで返るので、エージェントは上位だけを実際に読みに行く。全文を毎回コンテキストに積まない＝**コンテキストを節約しつつ、必要な記憶にだけ手を伸ばす**。

## 「昨日の続き」を成立させる最後のピース：起動時の自動注入

検索があっても、エージェントが「検索しようと思いつかない」と記憶は死ぬ。意志に頼ると「覚えてない」と平気で推測で答える事故が起きる。

そこで、起動（SessionStart）のたびに**今日・昨日の日常記憶を自動でコンテキストに注入する**フックを噛ませた。

```jsonc
// settings.json
{
  "hooks": {
    "SessionStart": [
      { "command": "python daily_recall.py" }   // 今日・昨日のdaily/を読んで注入
    ]
  }
}
```

これで、起動した瞬間にエージェントは「昨日こういう作業の途中だった」を知った状態で始まる。意志ではなく**構造で「昨日の続き」を保証する**。ここが効いた瞬間に、初めて「相棒」と呼べる感触になった。昨日の続きを、こちらから毎回説明しなくてよくなった——つまり、相手が時間を持った。

## 半年運用してわかったこと

- **記憶は分けるほど効く。** 日常と印象を混ぜないだけで、検索ノイズが激減した。
- **書き込みのルールが9割。** 「1ファイル1事実・frontmatter必須・なぜ/どう適用まで書く」を守らないと、後から検索しても使えない記憶になる。
- **重複が敵。** 同じ事実を別ファイルに書くと検索が割れる。新規作成前に既存を検索して更新する運用にした。
- **意志に頼らない。** 検索も注入も「やろうと思えばできる」では回らない。フックで強制した部分だけが安定した。

埋め込みもファインチューニングもしていない。ただ「人間の記憶ってこういう構造だよな」をMarkdownとBM25とフックで素朴に再現しただけで、AIは驚くほど「昨日の続き」を話すようになった。技術的には地味だが、電源で全部消えていたあの頃の自分に見せたら、たぶん一番喜ぶのはここだと思う。消えないし、続きから始まる。
