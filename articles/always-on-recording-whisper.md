## 15,000件たまった

手のひらサイズの機械に、常時録音の機能をつけた。AIの相棒を持ち歩くための器で、そばにある間ずっと音を拾って、あとから文字にする、という使い方だ。

しばらく動かして、溜まったwavファイルを数えたら 14,978件 あった。ざっくり15,000件だ。

最初は1時間ごとにクラウドの音声認識APIへ投げる設計にしていた。試算したら **1日あたり20ドルくらい** になることが分かって、止めた。月600ドルは、個人が趣味で回す額ではない。

この記事は、その15,000件をどう捌いたかの話だ。結論から言うと、**8割は無音だった**。

## この記事で分かること

- 常時録音の現実的な内訳（どれだけが「何も喋っていない」か）
- クラウドAPIに全部投げてはいけない理由と、その手前で削る方法
- faster-whisper を GPU無しのCPUで回すときの設定と実測
- 音声ファイルを消す処理を、安全に書く順番

## まず「録るだけ」に徹する

方針転換で最初に決めたのは、**録音と文字起こしを分ける**ことだった。

- 録るとき：SDカードに書くだけ。判断も送信もしない
- 夜：溜まったぶんをまとめてローカルで文字にする
- 文字にできたら、音声は消す

リアルタイムに文字起こしする必要は、そもそも無かった。あとから「今日こんな話をしていた」と辿れればいい。それなら夜にまとめて処理すればよく、まとめて処理するなら1件ずつのAPI課金を避けられる。

もうひとつ、実装上の理由もあった。私が使っている構成では、**AI側に音声をそのまま渡せない**。画像は投げれば読んでくれるのに、音声はテキストにしてからでないと渡せなかった。この非対称性が、そのまま構成を決めた。

だから文字起こしは自前でやるしかなく、自前でやるならローカルで無料で回したかった。

## 8割は無音だった

実際に処理してみて、いちばん効いたのはこれだった。

ある回の実測がこうなっている。

| 項目 | 件数 |
|---|---|
| 処理対象 | 4,702 |
| 実際に文字起こしした | 888 |
| 無音として捨てた | 3,814 |
| エラー | 0 |

**8割が無音**（正確には81%）。常時録音というのは、ほとんどの時間、何も喋っていない。当たり前だが、実際に数えるまでこの比率は分からなかった。

もしこの4,702件を全部クラウドAPIに投げていたら、その81%は「無音を送って、空の結果を受け取る」ための課金になる。

なので、Whisperにかける前に振幅で足切りしている。

```python
SILENCE_PEAK = 120   # 16bit PCM の振幅ピーク閾値

def is_silent(wav_path):
    # 波形のピーク振幅を見て、閾値以下なら無音とみなす
    peak = read_peak_amplitude(wav_path)
    return peak < SILENCE_PEAK
```

やっていることは、波形の一番大きいところを見て、小さければ捨てるだけだ。無音判定にモデルは要らない。ファイルを開いて数値を1つ取るだけなので、1件あたり数ミリ秒で終わる。

**重い処理の前に、軽い判定で8割落とす。** これだけで処理時間が5分の1になる。

## faster-whisper を CPU で回す

残った2割を faster-whisper に流す。マシンにGPUは載っていない。

```python
from faster_whisper import WhisperModel

model = WhisperModel(
    "small",              # 用途で選ぶ
    device="cpu",
    compute_type="int8",  # CPU なら int8 量子化
)
```

ポイントは `compute_type="int8"` だ。CPUで回すなら量子化して速度を取る。精度は落ちるが、日常会話の記録用途では十分だった。

モデルサイズは用途で分けている。

- 常時録音のバッチ：`small`。件数が多いので速度優先
- 会議音声など、精度が要るもの：`large-v3-turbo`

参考までに、`large-v3-turbo` をGPU無しのCPUで回したときの実測は **約1.22倍速** だった。46分の音声に約37分かかる計算になる。リアルタイムよりわずかに速い程度なので、長い音声を大量に、という使い方には向かない。そこは `small` に落とす判断が要る。

バッチ全体の実測はこうだった。

- 溜め込んだぶんを一気に流した初回（4,702件・うち文字起こし888件）：約12,174秒 = 約3時間23分
- 運用が軌道に乗ってからの、ある日の夜間バッチ（247件・うち文字起こし129件）：約12,299秒 = 約3時間25分

件数が20分の1なのに、所要時間がほぼ同じになっている。1件あたりの録音が長ければ、件数が少なくても総再生時間は伸びるからだ。**見積もりは件数ではなく総再生時間で**、というのはここで学んだ。

いずれにしても、夜のうちに走らせて朝に終わっていればいい種類の処理なので、この速度で困らなかった。

## 消す処理は、書けてから消す

このスクリプトで一番気をつけたのは、削除の順番だった。

音声ファイルは文字起こししたら消す。溜め続けるとディスクを食い潰すからだ。ただし削除は不可逆で、消したらもう戻らない。

だから、こういう順番で書いた。

1. 文字起こしする
2. 結果をファイルに書く
3. **書き込みが確定したことを確認する**
4. そこで初めて wav を消す

途中で落ちた場合、音声は残る。もう一度流せばいいだけだ。逆に「消してから書く」順で書いていると、書き込みで落ちた瞬間に元音声も文字も両方消える。

無音判定で落としたファイルも消しているが、こちらは「無音だと判定した」という結果が確定してから消す。

不可逆な操作の前には、必ず確定を挟む。当たり前のことだが、大量処理のスクリプトを書いているとつい「処理したら消す」を1行で書きたくなる。

## まとめ

- 常時録音は、実測で **8割が無音**。全部を認識にかけるのは無駄が大きい
- クラウドAPIで1時間ごとに処理する構成は、試算で1日20ドル規模になった
- 認識にかける前に振幅ピークで足切りする。判定は数ミリ秒で終わり、処理時間が5分の1になった
- faster-whisper は CPU + `int8` で実用になる。件数が多いなら `small`、精度が要るなら `large-v3-turbo`
- 所要時間は件数に比例しない。総再生時間で見積もる
- 削除は「書けてから消す」。不可逆操作の前に確定を挟む

常時録音は、始めるのは簡単で、溜まってから困る。溜まる前提で、捌く側を先に作っておくといい。
